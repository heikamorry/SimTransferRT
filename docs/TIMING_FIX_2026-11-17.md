# 64 KiB Release 时序修复与复测（2026-11-17）

这轮修复来自 `release-test-01` 的双端报告：40,022 帧、1,841,012 个数据报均已对账收齐，发送失败与补发均为零；仍有 38 次采样间隔偏差达到 1 ms、6 次首发分片间隔偏差达到 1 ms。完整交付与时序达标分别判断。原始手工报告及旧发行包保留。

## 修复内容

1. **到期采样优先。** 等待返回后先处理 Stop/轻量取消；若采样已经到期，直接执行采样，不再先轮询 UDP、普通控制入口或普通命令。接收、命令的每个有界项之前重新检查截止时间。反馈分阶段续处理，避免持续慢接收或慢控制轮询饿死已经入队的 SetMask/NACK。尚未执行的 SetMask 不抢占已到期的采样，实际应用之后的下一次采样生效。
2. **过载时仍可停止。** 原生 CLI 的信号取消使用独立只读旗标检查，不依赖可能被持续过载推迟的普通控制轮询。最后一次空接收等慢操作也计入 50 µs 阶段预算命中；预算限制调度次数，无法中断单个正在执行的系统调用。
3. **保留每类最严重异常。** `timing_trace.version=3` 按 6 类原因各保留最大的 2 次，最多 12 窗；数值相同时保留较早触发。新增首发分片间隔和慢 send 触发，保留准确的相邻采样/发送时间、计划时间、片号、发送顺序及首发/重复/补发身份。窗口有界且允许重叠；它是最坏事件取样，不是全部事件或代表性统计样本。
4. **修正接收完成测量。** `receiver_timing.version=2` 保留旧的最后一片进入解析前的跨度，另加最终 CRC、拼接和模块校验后的新时钟读数。新增 `frame_first_seen_to_validation_complete` 和 `last_ingest_to_validation_complete`，不把旧值改名当成新的完整处理耗时，也不改变 NACK 的逻辑时间。
5. **补齐严格验收。** `acceptance_schema_version=4` 的整体通过必须包含首发分片间隔偏差严格小于 1,000 µs，且直方图数量与发送次数/分段数、超限计数一致。缺失或不一致为未验证。新增 `A64` 明确表示 65,536 B 完整逻辑帧；原 `A1` 仍为 1 MiB。

DATA/NACK 格式、CRC、20 ms 采样目标、15 ms 首发目标、三槽缓存及原有重传规则保持原语义。没有放宽时序阈值，也没有修改系统优先级、绑核或电源设置。

极端过载下，如果每次组帧或 send 都超过 20 ms、持续没有采样间隙，普通控制和快照仍可能延后；Stop/取消仍在调度边界优先处理。单次调用运行期间不能被这层调度抢占。

## 证据解释

- trace 计数满足 `total_triggers = triggers_not_captured + windows_evicted + retained_windows`。未入选和入选后被更严重事件替换分别计数；滚动覆盖不是丢包。
- 事件 `sequence` 是记录顺序。慢阶段结束后才补记起点，因此时间戳不保证按 sequence 单调递增。以对应起止时间解释跨度。
- `context.has_previous=false` 时忽略 previous 字段；`has_planned=false` 时计划时间输出 null。补发没有假定的首发计划时间。
- send 结束时间在诊断窗口拷贝之前读取；首发完成耗时使用实际最后一次 send 返回时间，避免把诊断保存本身算进本次 send。
- 接收完成测量是接收进程内的用户态跨度，既不是跨机器单向延迟，也不是网卡硬件时间戳。没有 ACK/SUCCESS 限制发送端的在线确认能力；双方完整帧清单对账仍能提供离线收齐证据。
- Debug、Release、GUI、CLI 和不同桌面负载的结果不可直接当成受控 A/B 因果实验。环回收齐不能证明物理网卡/交换机链路或硬实时达标。

## 重现命令

在仓库根目录的 PowerShell 执行：

```powershell
cmd /d /c scripts\build.cmd Release
cmd /d /c scripts\test-network.cmd Release
cmd /d /c scripts\test-diagnostics.cmd --suite short --cases A64 --seconds 600 --out artifacts\udp-diagnostics\timing-fix-retest
```

这里的 `short` 表示可自定义场景与时长；既有 `--suite long` 固定运行 A0-drain/A1，不采用自定义 A64 排程。时序未达标会返回退出码 1，同时保留完整原始报告，不能据此误判测试未执行或工具崩溃。

## 严重停顿的时间线证据

新 trace 计数、按原因配额与淘汰计数均闭合；保留窗口确实包含统计中的最大采样偏差。零分片超限、零 ≥1 ms send 时不生成这两类窗口，属于正确的空观测。

| 从首次采样起算 | 当前帧 ID | 实际采样间隔 | 原 deadline 迟到 | 跳过时隙 | WaitEnd 至 Sample |
|---|---:|---:|---:|---:|---:|
| 333.863870 秒 | 16,689 | 123,413 µs | 103,870 µs | 5 | 22 µs |
| 399.046229 秒 | 19,943 | 125,959 µs | 106,229 µs | 5 | 18 µs |
| 435.575495 秒 | 21,765 | 115,416 µs | 95,495 µs | 4 | 7 µs |

这三次约 109–110 ms 的长跨度均落在 `WaitBegin → WaitEnd` 内；返回之后直接采样，前面没有插入 receive/普通命令。后续短周期回到原定节拍，相关偏差也保留计数。它们说明本轮发现的长尾主要在等待区域，而已到期采样被普通工作推迟的旧调度顺序已被修正。

`maxSampleLatenessUs=15,495` 是跳过超期周期之后的剩余迟到，不能用于否认 106,229 µs 的原 deadline 迟到。原计划时间由新 trace context 保留，整体采样验收使用全部实际相邻间隔，不使用这个较小旧计数掩盖跳采。

目前等待实现为 Windows 高分辨率 waitable timer（失败则 sleep_for）加末段 80 µs 自旋。现有时间线未记录具体等待分支、系统调用返回码或线程运行状态，因此只能定位等待区域，不能证明具体是计时器、线程未获得 CPU、进程暂停或其他原因，更不能认定是 socket 丢包/阻塞。接收侧也观测到最大 118.607 ms 的 select 跨度，但无对应时刻，不能强行与发送侧配对。剩余根因需要带时刻的等待分支记录及系统调度跟踪；在获得这些证据前，不将提高优先级或扩大自旋视为已验证修复。
