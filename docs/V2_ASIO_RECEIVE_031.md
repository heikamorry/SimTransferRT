# SimTransferRT 0.3.1 收发复测

0.3.1 用于复测电生理大帧在接收线程短暂停顿后的补发情况。两端均可导出报告，顶层 `product_version` 标识软件版本。

### 接收处理

接收线程每批最多处理 64 个报文，时间预算 500 µs。首批预算耗尽后，线程可以立即再读一批。队列已空时立即检查定时器，持续可读时第二批结束就检查。接收到同模块新帧或片号缺口触发的首轮请求仍立即处理。2 ms 尾部检测、后续 10 ms 间隔和三轮上限遵循 V2 协议。线程在每次读取前检查停止请求。

每轮增量最多 64 次报文处理，目标时间预算 500 µs。单包处理时间及操作系统抢占均可使实际用时超过预算。真正缺片且同时有持续流量时，定时检查可能延后一个批次，因此评估补发时也要比较请求迟到和帧过期。

### 收益和代价

确定性回归中，电生理每帧 204800 字节、共 143 个分片。应用读到第 64 片后暂停 2001 µs，其余原片已在队列。旧顺序发出一条列有 79 个分片的 NACK，新顺序在此用例中请求 0 片，两种顺序各完成一帧。此数字衡量被消除的请求，现场补发量取决于已有多少尾片在系统队列中等待。

持续流入其他报文且真正缺尾片的测试覆盖三轮请求和过期。若第三轮截止时尾片已排到第 65 个位置，新顺序能消费这一帧。原包仍在空口、驱动中或排在续读预算之后时，应用仍可能请求补发。采样线程错过计划槽位由 `skipped_slots` 记录，本次接收调度改动对发送主机晚醒没有直接收益。

### 实机对照

1. 两端记录软件版本、连接方式（两端分别记录 Wi-Fi 或有线）、网卡、频段和测试时长。先启动接收，再启动发送。停止发送后留出收尾时间，待接收计数稳定再停止接收并导出两份报告。
2. 同一对设备先用旧版参数原样复测新版，再只修改发送端 GUI 的“已知路径上限（Mbps）”，可分别试 300、200。每轮保持 NDI 60 Hz、4 工具和电生理 204800 字节、50 Hz；同组尽量重复。若可接网线，再做同参数对照。
3. 优先比较已完成/已消费帧、过期帧、电生理首发超期和 NDI 跳采。补发开销取发送端电生理 `retransmissions / (datagrams - retransmissions)`（此公式用于未注入重复/丢包的测试）。接收端另看每个观察帧的尾部触发数。

在项目的串行化估算中，电生理单帧在 961 / 300 / 200 Mbps 下分别约需 1.83 / 5.85 / 8.78 ms。降低上限可以把一帧的提交摊开，同时会占用更多的 18 ms 首发时间预算。各档的实际完成时间、超期次数和过期帧应通过报告比较。

| 接收报告字段 | 解读 |
|---|---|
| `receiver.modules["2"].firstTailIdle`、`firstTailNewFrame` | 每帧首次判定尾部时，按 2 ms 无新片或同模块更新帧到达计一次。此前已因中间缺片发过 NACK 的帧也计入，并沿用原定补发时间。 |
| `fragment_outcomes.retry.accepted` | 补发先于其它副本填入空缺的分片数，包括最终过期的帧 |
| `fragment_outcomes.retry.after_complete`、`original.after_expiry` | 在帧完成后到达的补发片和在帧过期后到达的原始片，两个值均在模块的 `fragment_outcomes` 下 |
| `expired_frame_samples` | 每模块最先 8 个过期帧的编号、已收片数、总片数、请求轮次及过期原因 |
| `receiver.receive_loop.extra_batches`、`extra_datagrams`、`forced_timer_polls` | 实际读到额外报文的续读批次数、读取的额外报文数、两批预算耗尽后执行定时检查的次数 |
| `nack_batches_socket_readable`、`nack_batches_socket_not_readable`、`nack_batches_socket_readability_unknown` | 每组非空 NACK 生成后、发送前探测一次 socket。可读说明有数据排队，具体模块及帧号须与逐包证据核对 |

旧版无线报告中电生理补发相对首发为 14.73%，接收端记录 47 个过期帧。两份旧报告收尾时间不同，适合用于观察问题规模。比较版本收益时使用覆盖相同发送窗口的成对报告。
