# 全流发包抖动的进一步修改报告

2026-11-26 · Windows x64 Release · 本机 IPv4 UDP 环回 · 1,000 Mbit/s · 模拟 NDI 4 工具、60 Hz · EP 204,800 字节、50 Hz

## 当前决定

保持 NDI 交接提前量 0 µs、Asio 操作复用关闭、交换间隔试验默认关闭。第 10 节的 600 秒正式环回使用了交换间隔试验构建。全流发包峰值为 428 µs，4,325,999 个间隔均在要求内。NDI 和 EP 控件更新仍分别有 62 和 11 帧超期。

### 第 8 节 GUI 修订版的阶段结果

采用 GUI 修订版，保持 Asio 操作复用默认关闭。正式关闭追踪的 600 秒真实环回中，**全流、NDI 和 EP 发包抖动峰值分别为 435、379、432 µs，三项均零违规**。全部 66,000 帧成功首传、收齐、消费并更新控件。联合验收仍失败，失败项为 NDI/EP 界面更新，峰值分别为 154.409/165.864 ms。宿主基础测试 13/13 通过。正式明细和归因边界见第 8 节。正式长测（`build/jitter-gui-20261126/loopback-zmxryssp/formal/joint.json`） · 逐帧诊断（`build/jitter-gui-20261126/loopback-zmxryssp/diagnostic/joint.json`）

### 立项时的判断

**建议先在可正常收包的宿主确定超限包来自哪条路径，再做一个局部改动。** 已捕获的全流超限样本中，EP 连续 143 个分片的发送进度落后，尾片与下一份接近准点的 NDI 数据之间形成了过短间隔。历史宿主运行还出现过另一种现象：NDI 准时准备好，却迟迟没有开始发送。两者需要不同的修改。当前证据支持继续保持 NDI 交接提前量 0 µs，优先调查 EP 提交成本及发送线程在异常窗口内的运行状态。

## 1. 为什么两路都按时完成首传，全流仍会超标

全流验收逐一比较相邻报文的**实际本地发送开始间隔**和**原计划间隔**，涵盖 DATA、实际发出的重传和状态包；所有观测均须严格小于 1,000 µs。首传截止期衡量整帧采样到所有初始分片本地成功完成的总时间。一个 EP 帧可以在 18 ms 内完成，同时把某个跨模块包间隔挤短超过 1 ms。[验收实现](../src/v2/Engine.cpp) · [报告口径](../src/v2/RunnerReport.cpp)

对下面这对计划时刻递增的数据包，记实际时刻为 S、原计划为 P，则间隔偏差等于两包各自迟到量之差的绝对值。对于重传等可能导致计划时刻倒退的组合，现有代码将期望间隔下限取零。

| 75 秒诊断中的最坏包对 | 相对各自原计划 | 与验收的关系 |
| --- | ---: | --- |
| 前包，EP 帧 332 的末片，索引 142 | 晚 1,900 µs | 帧内索引 100 开始时晚 598 µs，到索引 102 已晚 1,688 µs |
| 后包，NDI 帧 399 的首片 | 晚 41 µs | 相邻间隔实际 9,726 µs，计划 11,585 µs，偏差 **1,859 µs** |

**收益尺度可以算出。** 固定这一对的 NDI 时刻与计划，须把 EP 尾片至少提前 **860 µs**，才能从 1,859 降至 999 µs。若均摊到首末片之间的 142 个间隔，约为 **6.06 µs/间隔**；也可以通过消除少数长停顿达到。该帧索引 100、101 从提交开始到观察本地完成各耗 609、438 µs。旧诊断把这两段耗时各记作一个整体，无法再区分 API 发起、完成处理或中途被抢占。人为推迟后一个 NDI 包也能改变该数字，同时会损害另一条流的时序，所以不作为优化手段。逐包原始数据（`build/four-metric-20261126-120839/gap-trace.json`）

## 3. 修改顺序与停止条件

**第一步是补齐宿主违规包对。** 以同一候选 Release、普通 PowerShell、可见 GUI、默认 0 µs 做 600 秒基线，核对两路完整收包和控件更新。建议给联合测试入口增加仅诊断时启用的选项，保留原 SPSC 路径，记录每次 ≥1,000 µs 的前后两包、模块/帧号/片号、原计划、实际开始与完成。为关联前一帧，保留最近 EP 帧分片记录以及 NDI 的就绪、入队、出队时间。使用预分配有界缓冲、独立的全量违规计数和溢出计数，后台或结束后导出。若记录不全，只对留存样本归因。现有逐片拆分来自独立 CLI；正式 GUI 入口还需接入。开启完整交接跟踪会切换队列路径，不适合直接评价默认 SPSC 的交接成本。[运行器](../src/v2/Runner.cpp) · [联合测试入口](../tools/run_release_loopback.py)

对保留下来的异常，使用报告里的发送线程 TID 和 QPC 时钟锚点对齐 ETW，检查相同 CPU 上的切换、Ready 与 DPC/ISR。仓库已有环形调度采集配置及分片对齐工具；现有配置记录调度和中断事件，分配调用栈需另开短时采样。诊断开启和关闭应各跑基线，正式验收关闭额外追踪。[WPR 配置](../tools/handoff_etw/SchedulerMemory.wprp) · [分片对齐工具](../tools/handoff_etw/align-fragments.py)

| 宿主违规窗口实际显示什么 | 只试一个改动 | 边际收益与退出条件 |
| --- | --- | --- |
| EP 末片累积迟到，发送线程持续运行，提交内部出现真实堆分配热点 | 优先试传输实例私有的 Boost 关联分配器，只复用异步操作状态。保留现有数据槽、单在途和逐包提交；尺寸、对齐或容量不匹配时回退。记录实际堆分配、命中和回退 | 只有异常帧的 API 提交耗时和尾片迟到量同步下降才保留。若每间隔仅节省 1 µs，在该帧 142 个间隔上理想收益约 142 µs，单独不足以追回 860 µs |
| EP 提交内部主要花在取槽或复制 | 在诊断版分别标记取槽、用户态复制和 Asio 调用。复制确为热点才单独试验在具有异步寿命的槽中直接构造 EP 首发数据报 | 逐字节比对帧号、时间戳、CRC、长度，测试重传、故障注入和取消。固定时间戳含义，防止靠移动测点制造收益。64 槽已存在，当前引擎一次只跟踪一份在途提交，扩池的依据不足 |
| NDI 及时就绪，或 EP 提交中断时，发送线程处于 Ready/Waiting | 按同一窗口的栈和锁持有者验证；若是本进程快照或锁阻塞，仅移动被证实的临界区工作，保留采样、发送和反馈顺序 | 看同一类异常的就绪至取帧或暂停时间是否下降。若对应第三方占用、内核 DPC 或网络栈，把环境与软件结果分别记录，停止无证据的忙等、加线程或容器替换 |
| 反复出现的违规主要在提交返回后等待完成 | 才评估 EP 专用的两片在途原型。保留逐片原计划、发送节拍和 NDI 在分片边界的调度机会 | 要按 token 管理每片成功、失败、乱序完成和取消。本地 90 秒样本这一段总共仅 89 µs，现阶段优先级低。任何首传统计错误、重传异常或 NDI 回归即退回单在途 |

若栈显示大部分时间位于 Winsock/内核且线程一直在运行，先保留原始逐包时间戳并验证同一代码在宿主是否复现。仅把 Boost 换成直接调用 Winsock 仍会经过底层发送接口；目前没有可承诺的降幅。批量发送、推迟下一 NDI 帧、降低输入负载、扩大分片、改原计划时间或用平均值替代严格最大值均排除在这次验收修改之外。[传输实现](../src/network/AsioUdpTransport.cpp) · [发送与完成记账](../src/v2/Engine.cpp) · [Winsock 发送语义](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-wsasendto)

## 4. 怎样保护已经通过的指标

1. **比较方式。** A 为同一宿主的新基线，B 每次只启用一项候选。固定输入、链路档位、显示页可见性、电源模式和追踪状态，构建与其他压测分时运行。建议先 A/A 观察波动，再交替 A/B、B/A，每轮 600 秒。每轮保留程序哈希、CPU 时间、每项最大值、违规数和分母。短测用于筛错；不能合并多轮掩盖单轮违规。
2. **正式通过。** 每轮全流和 NDI、EP 各自发包偏差均须严格 <1,000 µs，违规为零。NDI 60 Hz、EP 50 Hz 在 600 秒分别产生 36,000 和 30,000 帧，已完成首传、接收端消费、GUI 逐帧更新三处对账。保留采样偏差 <1,000 µs、零跳采/队列丢帧和首传 NDI ≤15 ms、EP ≤18 ms，保留原容量及错误判定。两项 GUI 指标各自报告最大值和超期数，NDI ≤16,667 µs、EP ≤20,000 µs 才算通过。
3. **回退条件。** 任何原有通过项新出现违规、丢帧、数据错误，或从通过变为未测，均不推广。即使仍在阈值内，也把原有指标的峰值、超时、CPU 和 GUI 延迟与 A/A 范围对照；若在调换顺序后仍持续变差，撤回候选。重传、乱序完成、取消用定向基础测试单独覆盖。无丢包长测没有触发 NACK 时该项标记未测，不能代替重传回归。
4. **最终决策。** 先比较违规次数，再比较最大偏差及到 1 ms 的余量。次数下降但仍有一次超限，记为实验进展。采用达到原门槛且额外 CPU 成本最低的方案。制定计划时以历史数据估算改善空间。第 6 至 8 节给出本轮真实收包长测及逐项结论。

当前候选的第一轮宿主测试在仓库根目录使用普通 PowerShell。它会先跑基础测试，再自动监听 127.0.0.1、发送、切回接收页和导出 600 秒诊断报告。测试期间保持窗口可见、停留接收页。结果写入候选目录下新建的 `loopback-*` 文件夹，控制台打印完整路径。本次使用 A 和分片追踪定位宿主超限。正式 A/B 则使用同一驱动，双方均关闭追踪。

```powershell
py -3 -B tools/run_release_loopback.py --build build/jitter-candidate-20261126/Release --basic-tests --visible --seconds 600 --ndi-handoff-guard-us 0 --fragment-trace
```

## 5. 本轮实施方案及候选版本

采用同一份 x64 Release 做开关对照。A 使用原 Asio 分配方式，B 为每个异步传输实例预留一个 1 KiB 操作存储块。正常单笔在途时，下一笔提交可复用已归还的块。遇到重叠操作、超出容量或对齐要求时使用通用分配器。报告中的 `sender.operation_storage.hits` 和 `fallbacks` 计数对应实际分配路径。命中本身只证明开关生效。

诊断运行开启 `--fragment-trace`，导出 `sender.fragment_trace.global_gap_violations`。从首 64 对相邻违规包读取模块、帧号、片号、计划时刻、实际提交和本地完成时刻。条目写满后，报告仍维护全程违规总数、未保存条目数和独立的最坏包对。NDI 可以沿正常 SPSC 邮箱关联入队和出队时刻。诊断有额外开销，正式验收及其对照均关闭追踪。

如果前一包是原始 EP 数据包，使用该对的 `previous_ep_frame_index` 在同级 `previous_ep_frames` 中找到整帧的分片序列。同一帧仅保留一份。状态 `finalized` 表示序列已冻结，`pending` 表示帧仍活动，`unavailable` 表示取消等原因使完整序列不可用。

1. **确定改善空间。** 在同一台能真实收包的主机上跑 600 秒可见 GUI，先定位超限对。按前一包累计迟到、NDI 邮箱等待、出队后等待或完成等待分组，记录每组次数和最大值。某个阶段可追回的时间小于该对越线幅度时，只优化该阶段不足以使这一对达标。
2. **评估单一候选。** 固定 1 Gbit/s、NDI 60 Hz、EP 50 Hz、EP 204,800 字节、NDI 提前量 0 µs，保持同视图和负载。短轮 A/B/B/A 筛选候选，再用 600 秒同配置复核。每轮单独记录全流、NDI、EP 最大偏差及违规数，同看采样、首传、收包、GUI 更新和 CPU 时间。
3. **决定保留。** 新增违规或原通过项退化即维持默认 A。多轮均消除违规且已通过指标落在 A/A 波动内，才考虑将 B 设为默认。若 B 仅有分配命中而尾部没有可重复收益，转到真实超限窗口，结合发送线程运行/就绪状态定位。GUI 延迟依赖真实收包后控件实际更新，单独核对 NDI 和 EP 的最大值、超期次数及更新帧数。

本轮仅调整 Asio 操作存储和诊断观测。原分片大小、64 个数据槽、发送顺序、首传成功完成条件、间隔公式、严格阈值与 GUI 超期计算均沿用项目定义。

历史宿主 600 秒报告支持将 GUI 单独定位到消息等待阶段。下列三个时长分别取最大值，可能对应不同帧。

| 模块 | 收齐到 GUI 开始 | GUI 应用耗时 | 收齐到控件更新 | 超过一个模块周期 |
| --- | ---: | ---: | ---: | ---: |
| NDI | 117,598 µs | 275 µs | 117,674 µs | 601 / 36,000 |
| EP | 125,698 µs | 181 µs | 125,762 µs | 353 / 30,000 |

这组数据中，单帧控件应用耗时低于 0.3 ms，GUI 开始处理前的等待已经超过 100 ms。只有当前候选的宿主长测仍复现这个分布时，才继续调查接收通知投递、待处理帧队列和主线程占用。一旦新证据显示瓶颈转到控件应用内部，再按具体调用更换组件。历史 GUI 联合报告（`build/validation-loopback-20261126-1116/host-final-600/joint.json`）

### 交换间隔试验

`SIM_GUI_IMMEDIATE_SWAP=ON` 仅改变 Qt/VTK GUI 启动时请求的交换间隔，默认构建设为 OFF。此版本同时包含上文的小脏区冷缓存修复。Qt 将该间隔定义为可被平台忽略的偏好值，桌面物理呈现仍需单独测量。[Qt 官方 QSurfaceFormat 说明](https://doc.qt.io/qt-6/qsurfaceformat.html#setSwapInterval)

同一宿主运行 13/13 基础测试后进行了 30 秒应用追踪短测。两版的三维预览均有实际更新。初版背景缓存 / 本版 NDI 最慢更新为 22,241 / 19,575 µs，超期 54 / 27 次；EP 为 19,504 / 16,004 µs，两轮均无超期。全流发包峰值 474 / 614 µs，两轮均无超限。最慢 NDI 的窗口合成至交换重叠 8,085 / 7,717 µs，波形 Paint 重叠 3,232 / 2,480 µs。本版 Qt 报告进程请求值 0、顶层窗口格式 0、VTK 控件上下文格式 1。合成与交换仍实际占用慢帧窗口，不能把请求值当作实际延迟降至零，单轮前后差值也不能全部归于这个选项。交换间隔试验的应用追踪（`build/gui-swap-20261126/loopback-h9r54fi9/diagnostic/joint.json`）
