# SimTransfer V2 三档网络配置公共子方案

日期：2026年11月17日。交付性质：实施方案，尚未修改运行代码，也不代表新版本已经完成性能验收。

本文件是[SimTransfer V2 与 Aurora 完整升级方案评比](D:/SimTransferRT/docs/V2_AURORA_UPGRADE_OPTIONS_2026-11-17.md)的公共子方案。100Mbps、1GbE、2.5GbE切换是所有架构方案共同的必选功能；本文件不再作为整体升级方案的替代。

采用同一套V2协议和统一发送调度器，在SimTransfer中提供100Mbps、1GbE、2.5GbE三个网络档位。1GbE为首次启动默认值和首选档位；100Mbps用于现有链路联调及经验证的受限负载；2.5GbE用于已有高速网络或后续扩展。切换网络档位不改变协议字段、采样目标和验收阈值。

## 1 当前基础与修改定位

当前界面已有“链路容量估算”下拉框，包含100、1000、2500、10000Mbit/s，默认1000。`StreamConfig.linkMbps`和Qt/native CLI的`--link-mbps`已贯通。它们目前只参与旧版单组合帧15ms容量检查；`PacketPacer`没有读取链路速率，仍使用固定规则计算包间隔。

本次应升级现有能力：把容量输入变成三档运行配置，接入V2容量预检、全局发送预算、日志和验收报告，并补上设置持久化。不能只删掉10G选项、改几个界面标签就视为完成。

当前协议实现仍是V1组合帧。V2的独立模块、状态包、片号列表NACK、各模块四帧缓存及独立接收消费，必须作为同一升级工作的基础部分实现。已有Windows UDP处理、Stop优先、有限工作预算、诊断时间线和接收校验完成计时继续保留。

## 2 输入条件与三档预算

| 项目 | 本方案采用的口径 |
|---|---|
| 电生理最大数据量 | 用户给定200KB；暂按200KiB＝204800字节作保守预算，配置界面同时显示字节数。实际源若为200000字节则按真实长度发送，不填充。 |
| NDI数据 | 优先单次Aurora标准BX定位回复；H条有效工具记录对应11＋42H字节。实际型号和最大工具数尚未知。 |
| NDI接收缓冲 | 建议16KiB，仅为单次标准BX回复的容量保护，不作为固定发送帧长。VSIU原始数据、聚合多次回复和额外业务封装另算。 |
| 频率和期限 | 网络模型保留NDI约60Hz、首发≤15ms；电生理50Hz、首发≤18ms。真实Aurora模式与频率另行验证。 |
| 状态与重传 | 状态最高优先，首发次之，补发最低；状态峰值、突发量与故障注入条件需要进入测试配置。 |
| 链路假设 | 有线全双工IPv4、MTU1500，无VLAN或隧道。额外封装出现时应增加预算开销。 |

以下示例假设NDI返回40条有效BX记录，即1691字节；40是计算场景，不是已确认的设备能力。按NDI60Hz、电生理50Hz、每帧电生理204800字节计算，NDI每帧2片、电生理每帧143片，首发合计约7270包/秒。

| 网络档位 | 产品定位 | 两路首发平均线路占用 | 电生理单帧出线理论下限 | 同步产生两帧的出线理论下限 |
|---|---|---:|---:|---:|
| 100Mbps | 备选，现有网络联调 | 88.664% | 17.55088ms | 17.70248ms |
| 1GbE | 首选，默认 | 8.8664% | 1.755088ms | 1.770248ms |
| 2.5GbE | 备选，扩展 | 3.54656% | 0.7020352ms | 0.7080992ms |

这是容量计算，不是软件发送耗时或达标承诺，未计状态、补发、背景流量及主机处理。100Mbps场景中，两帧同步产生时距18ms仅剩约0.298ms。若NDI回复达到10721字节的数量字段保护边界，同步两帧在100Mbps上至少需18.474ms；该配置即使平均流量低于100Mbps，也不能满足全部首发期限。10721字节不代表设备支持255个工具。

计算式为：分片数N＝ceil(F/1436)，数据帧线上占用W＝F＋102N字节。102包括36字节协议开销，以及IP/UDP、以太网头、FCS、前导码和帧间隙。任意UDP数据报应按其实际UDP应用长度加66字节计入本方向预算；状态包不能套用DATA头长。反馈方向和本机处理负荷分别计量。

不设置“三档统一限制到80%带宽”的默认策略。它会把100Mbps有效预算压到80Mbps，使电生理200KiB场景在数学上就无法按期发送。状态和补发余量必须依据实际负载和明确的测试条件核算，而不是通过固定百分比掩盖不可行组合。

## 3 界面与切换流程

网络页将“链路容量估算”改为“网络档位”，只显示三个日常选项：

- 100Mbps（备选）
- 1GbE（推荐）
- 2.5GbE（备选）

首次启动选择1GbE；以后恢复上次用户实际选择。保留“推荐”标记，不因机器当前网口较慢就偷偷改写用户选择。

下方显示四类独立信息：所选档位、检测到的本机网口速率、用于调度的有效预算、当前业务负载的估算结果。另显示NDI和电生理的实际帧长/声明上限、首发期限，以及容量检查说明。例如：“所选1GbE；本机连接100Mbps；当前按100Mbps预算；电生理首发余量较小”。

三个选项仅在空闲状态可切换。准备、发送和收尾期间保持禁用。操作流程为“停止当前运行→选择档位→重新开始”；不新增运行中的热切换，以免一个统计区间混入不同节奏和缓存状态。

保留现有快速Stop语义：到调度边界后停止，未发片及取消的补发如实计入报告，不承诺无损排空。只有工作线程真正结束、最后快照归档之后才允许新档位启动。未来若增加平滑停止，应另设有界功能，不改变Stop的快速响应职责。

新一次运行创建独立本地run_id，锁定一份不可变配置，分别保留各模块下一帧号和状态序号；不在UDP包中私加run_id或版本字段。报告不能把两次运行的分母、抖动分布和超期计数混合。设备或接收端重启时按独立会话重置约定协调，不能仅凭本地run_id判断线上报文所属会话。

具体过渡规则：仅换档、设备和接收端持续运行时，续用各模块帧号、状态序号及时间域，取消旧的待发/补发任务，已离开主机的旧包仍按原序号和时序规则处理。设备或接收端重启、序号或时钟重置时，协调双端重建状态并优先换用新的数据/反馈端口隔离旧包；必须复用端口的部署，需先具备明确的旧包隔离措施，禁止自动复用序号和时间起点。新run_id和短暂等待均不作为线上隔离的证明。

## 4 配置和兼容性

新增网络档位枚举与共享解析函数，避免GUI、Qt CLI、native CLI各自实现一套转换。三档映射为100000000、1000000000、2500000000 bit/s，内部容量计算使用足够宽的整数及分数时钟累计，避免截断误差。

拟增加CLI参数`--network-profile 100m|1g|2g5`。保留`--link-mbps 100|1000|2500`作为兼容入口；两者同时指定且不一致时明确报配置错误，不按参数顺序覆盖。旧V1脚本的其他容量值，包括10000，保留在明确的旧版路径，不伪装成V2三档之一。V2日常界面保持三个选项。

使用现有QSettings机制保存新档位。旧配置没有该字段时默认1GbE；无效新值恢复为1GbE并记录原因。旧IP、端口、帧号和其他设置保留。CLI使用自身默认值或显式参数，不受GUI上次选择影响。

协议版本与网络档位独立：V1保留原有线格式、三槽缓存与原有节奏行为；V2使用新版线格式和各模块四帧缓存。切换网络档位不顺带切换协议版本。旧版报告继续可读，V2新增字段使用明确的报告版本和兼容解析。

## 5 容量检查与实际网络信息

启动预检覆盖平均带宽、单帧最短出线时间，以及两模块共同或错相产生时的截止窗口。它是可行性筛查，不是网络时序实测，也不是完整的最坏情况可调度性证明。

15/18ms的起算与结束边界必须独立确认并统一到双端报告。分别保留设备采样时刻、主机完整帧就绪时刻、本地send返回时刻及可取得的网卡出线时刻；只有共同时间映射有效时才计算跨时钟跨度。若期限从设备采样完成起算，Aurora到主机的串口/USB传输也要计入，不能在容量预检中把主机就绪时刻偷偷改成起点。以1691字节、921600波特、8N1为条件例子，仅回复串行化约18.35ms，可能已经超过NDI的15ms；这不是当前未知设备的实测，却说明更快UDP网口不能补偿上游延迟。

- 已证明容量不足：正常实时运行不接受该配置；可以使用现有明确的格式/过载测试入口观察行为，但报告保留失败，不放宽期限。
- 计算未发现冲突，但余量较小：允许运行并突出说明剩余时间，以实际验收判定结果，不引入未经约定的隐含通过阈值。
- 工具上限、状态峰值或实际路径未知：标明对应假设和未验证项，允许功能联调，不能宣称最坏负载已获保证。

NDI未知工具数时，分别展示“实际已观察长度”“设备或测试模型声明最大长度”“接收缓冲容量”。不能把16KiB保护缓冲当典型数据，也不能凭一次小回复证明以后所有帧都很小。启动模型和运行中长度变化均需检查；超过声明上限时记录异常和容量结论变化，不能静默截断、压缩、降频或丢弃来维持表面达标。

本机网口检测在非实时线程执行，通过目标路由和绑定地址匹配实际接口。普通网卡的连接速率只代表本机这一跳，不能证明交换机、对端或整条路径同速。远端/交换机限制由现场配置或额外证据记录，不虚构自动发现结果。

有效调度预算取所选档位与已知更低限制中的较小值，界面和报告保留每个输入及来源。选择2.5GbE而本机仅协商到1Gbps时，不按2.5Gbps发送；选择100Mbps而接在千兆网口时，可以按百兆预算节流，但该测试仍是千兆物理链路上的软件限速，不能冒充百兆实网。

检测失败、无线连接、VPN、虚拟接口或环回地址均明确标注适用范围。环回允许验证协议和软件调度，但物理链路与真实出线项目仍为未检测。实际速率下降时重新评估并记录事件，不能把降速前后的运行直接作为同一稳定工况通过。

## 6 三档如何影响发送

保持两个独立的采集/准备入口和一个统一发送出口。每模块维护不可变帧数据、设备采集标识、时间映射信息、帧号、截止时间和四帧重传缓存；界面、文件读取和详细报告生成不进入逐包关键路径。

新增全局线路预算器，所有状态、DATA首发和DATA补发都按实际数据报长度消耗对应发送方向预算。满长1472字节UDP包在三档上的理论线路占用分别为123.04µs、12.304µs和4.9216µs。这些是容量约束，不是要求Windows精确睡眠相同时间，也不保证更高档位下程序实际耗时按比例缩短。

统一调度器使用绝对时间、字节累计及每模块截止时间规划发送，不再直接套用旧版对所有负载固定的20µs规则。时间量化采用累计计算，避免百兆数百包逐次向上取整吃掉本已有限的期限余量。迟到后限制追赶额度，禁止积累整帧突发并一次塞满内核队列。

优先级仍为状态、首发、补发。首发内部结合最早截止时间和模块连续进展选择下一片，避免某模块长期被另一模块挤占。NDI只有少量分片时，在全局预算内尽快完成，不能为了“均匀”把两片摊到整个15ms，导致接收端按原有2ms无新片规则错误触发尾部NACK。

补发只使用不影响已知首发和下一采样期限的空档，同时限制队列长度、待处理工作量及缓存过期任务。状态峰值必须纳入条件；若无上限的状态流持续占据最高优先级，不能保证数据期限。不得未经补充约定合并或省略“每次变化都应发送”的状态。

三档使用同一套算法，通过速率参数、当前负载和期限计算计划；不维护三套协议或三套各自不同的验收逻辑。协议中的2ms尾片检测、10ms重试间隔、三轮请求及模块隔离不随网络档位改变。

## 7 日志与六列验收表

每份报告记录所选档位、协议版本、实际检测接口速率及时间、有效预算与来源、环回/实网类型、各模块帧长分布和声明最大值、状态/重传负载、计算公式版本及预检结果。理论值与实测值使用不同字段。

继续使用“要求、测量口径、阈值、实测值、通过/失败/未检测及原因”六列结构，三个档位保持相同的协议阈值。

首次形成的采样计划、发送计划和原始截止时间必须保留，不能被晚醒后的重排覆盖。调整后的due另记，原计划偏差、调整量、实际发送时间和最终是否超期分别导出，防止通过不断顺延计划让1ms超限计数虚假归零。

| 验收项目 | 必须保留的判定口径 |
|---|---|
| NDI首发 | ≤15ms；完整首发与未完成帧分别计数；本地提交与实际出线分列。 |
| 电生理首发 | ≤18ms；不能沿用旧版对所有模块统一15ms的验收行。 |
| 采样 | 分模块记录计划、实际、跳采、源设备重复帧；硬件采样与软件请求频率分开。 |
| 逐包间隔 | 全局发包间隔、每模块间隔、相对实际调度计划偏差分别统计；不能拿百兆合理的较长包间隔去减旧版固定20µs目标。 |
| 旧版1ms工程目标 | 最大采样/分片间隔偏差严格小于1ms继续作为附加工程目标，注明不是V2重新明确的原文门槛；不得按档位放宽。 |
| 接收重试 | 按模块验证缺口发现、2ms尾部判断、10ms间隔及三轮预算。 |
| 状态实时性 | 分别测状态确认到提交、接收和应用的延迟，以及突发量、序号和旧包丢弃；“立即”的数值口径未确定前不能宣称该项通过。 |
| 收发联合结果 | 计划采样缺口、已构建帧、首发、补发、接收校验完成、最终消费分别对账；后续补齐不抵消首发超期。 |
| 硬件与显示 | 未接入共同时间映射、未测真实出线或未实现显示时保留未检测；任何档位都不能仅凭本地send成功判完整验收通过。 |

报告记录Stop取消的未发和补发，保留低频快照及有界最坏事件追踪；配置不同的运行分别归档。收到旧schema报告时按旧口径展示，不能默认补出不存在的网络和模块字段。

## 9 实施顺序与验证

1. 固化V2字段和测量口径，统一文档NACK的CRC偏移与最小长度矛盾：按uint16片号列表推导的建议为`20＋2N`偏移、`24＋2N`总长、单片请求26字节。双端使用同一决定，不各自兼容矛盾格式。
2. 完成V2编解码、独立模块状态和Python参考接收，保留V1回归。先单端口功能联调，再进行多端口对照；同一网卡多个端口不会增加物理容量。
3. 接入三档配置、持久化、有效容量观察和统一线路预算，完成确定性测试；保留现有Stop响应和故障证据。
4. 用固定模拟负载完成三个档位的功能回归，再接真实网口做性能对比。模拟档位与真实网口速率分别记录。
5. 接入Aurora及电生理硬件，确认工具数、数据格式、实际采样频率和共同时间域；实现并验证接收端独立消费/显示。

建议的工程验证排程为每档先进行600秒联调，1GbE首选档至少进行2小时持续测试；100Mbps仅对预检没有证明不可能的声明负载做正常实时长测，不可行组合进入明确的负例/过载测试。以上时长是本次工程验证安排，不是协议原文指标。若2.5GbE或真实百兆网络不可用，保留对应实网测试为未检测，软件限速不能替代全部物理网络证据。

必须覆盖：三档首次默认和重启恢复、GUI与两种CLI一致、旧参数冲突处理、100M慢于所选1G的有效预算、环回标记、停止中不能换档、Stop未发片计数、各模块同帧号隔离、两个模块错相/同相、状态突发、重传压力、源帧长变化、CRC/丢包/重复/乱序、缓存覆盖、回绕、接收重启、日志开启时的主机负载。

性能对照使用同一软件版本、负载、运行时间和尽可能一致的主机条件；分别给出最大值、分位数、超限次数与完整分母。预检通过只表示没有被当前容量模型排除，最终通过仍需要完整实测证据。

## 10 已知接入条件与证据

Aurora API Rev.9描述常规40Hz，以及66Hz快速模式；快速模式的精度不确定度增加到2倍，串口可能进一步限速。标准BX/TX包含设备帧计数，没有直接提供共同时间域中的64位微秒时间戳。因此，三档切换不得自动改硬件采样模式，也不能把重复查询算成60Hz新采样。具体模式、源帧号与UDP帧号映射、串口/USB速率及同步误差需在硬件接入阶段落实。

新版协议的“状态立即发送”、状态峰值和显示有效期仍需明确测量口径；这些未定义条件不通过选择更快网档自动消失。
