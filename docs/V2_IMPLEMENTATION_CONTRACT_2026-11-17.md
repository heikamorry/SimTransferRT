# V2 方案 B 实现约定与使用说明

本文件对应 0.3.0 软件实现。真实设备、共同硬件时间域、实际网卡出线及真实电生理波形仍须独立验收；软件功能测试不能替代这些证据。

## 保留与构建

- 工作分支为 `dev`。实施前全部已跟踪文件、未跟踪正式文档及原有修改已另存源码压缩包、SHA256 清单和二进制差异补丁。位置：`artifacts/udp-stability/before-plan-b-20261117-153019/`。
- 原 V1 发送核心、接收工具、诊断修复与旧发行目录保留。新版使用独立 `src/v2/`、编解码及数据源目录。
- `scripts\build-v2.cmd` 在 `build/windows-v2-release/` 重新构建 Release 并执行 CTest，不覆盖旧 `build/windows-release/`。
- GUI 默认进入 V2；“V1 兼容窗口”按钮或 `SimTransfer --v1` 可使用原界面。原 CLI 参数及不指定版本的调用仍按 V1 处理；V2 必须显式指定 `--protocol v2`。两种线格式没有新增版本字段，应使用明确配置和端口隔离，不能依靠自动猜测。

## 线格式决定

1. V2 DATA、STATUS、NACK 均按文档偏移逐字段小端序编码，CRC32 覆盖尾部校验值之前的全部字节。DATA 最大 2MiB，1436 字节分片，UDP 应用层最多 1472 字节；STATUS 载荷最多 1444 字节，无分片、无 NACK。
2. 原文 NACK 表格中 `20+4N` 与 uint16 片号及 `24+2N` 总长矛盾。统一采用 **CRC 偏移 `20+2N`、总长 `24+2N`、一个片号时 26 字节、每包最多 724 个片号**。C++ 与独立 Python 实现使用相同决定，并通过双向字节向量校验。对外互通前应向对端同步本勘误。
3. 每个可分片模块各保留四帧。帧、补发、取消、重组均以 `(module_id, frame_id)` 区分。状态使用独立序号；状态优先于首发，首发优先于补发。
4. 接收端同模块缺口立即登记请求，2ms 无新片或同模块更新帧触发尾部判断，后续 10ms 间隔、最多三轮，第三轮后等待 10ms 作废。另一模块不能触发该模块尾部判断。
5. 不新增线上会话字段。换档续用各模块序号和主机单调时间域；设备／接收端重启或序号重置需明确协调，优先使用新端口隔离旧报文。GUI 接收端锁定本次首个合法源端点，重启接收才能重新选择源。

## 方案 B 数据路径

NDI 与电生理各有一个采集／准备线程。文件读取、BX 解析、成帧及首发 CRC 编码均在准备线程完成，经每模块最多四个不可变帧的队列交给唯一发送线程。各模块四帧重传缓存、全局线路预算及有界反馈处理由该发送线程拥有。停止标志在每包边界检查；源线程停止、缓存和队列清点结束之前保持运行配置锁定。

接收使用正式 C++ 重组／消费模型，GUI 独立刷新坐标、姿态、质量、有效性和电生理字节预览；Python 作为独立参考接收实现。两端均采用有界缓存、诊断与汇总，避免长测按每包无限增长。

## Aurora 数据与时间

- 一次完整标准 BX 回复原样作为 NDI 业务体。Valid/Missing/Disabled 记录分别为 42/10/2 字节，总长 `11 + 42V + 10M + 2D`；实际长度发送，16KiB 是保护上限，不作填充长度。
- 内层 Aurora 头／体 CRC16 与外层 UDP CRC32 分别验证。Missing、Disabled、出界或故障状态不冒充新有效坐标。质量指标不是准确率，5DOF 的零值不代表零误差。
- `INdiSource` 统一模拟、单次 BX 循环回放及可注入设备通信的 `DeviceSource`；真实设备查询、初始化、工具生命周期、跟踪、停止及时间映射在 NDI 线程执行。具体 COM/SDK 通信由有超时和取消约束的 `Exchange` 接入，当前没有提供已验证的真实串口驱动部署。
- 标准 BX 的设备 Frame Number 不是共同硬件微秒时间。软件保留源计数、重复、新源帧、逐工具计数缺口、重置、混合计数和映射误差。逐工具缺口总和不能解释成 UDP 丢帧数。
- 真实设备只有经过外部证据建立的共同时间映射才可生成协议时间戳；暂时未映射的帧计数并拒绝，后续仍继续读取，电生理不被阻塞。主机请求／就绪时刻保留为诊断，不能替代真实采样时刻。
- 主机查询频率、源新采样频率和 UDP 成帧率分列。模拟 60Hz 不证明 Aurora 硬件 60Hz；实际 40/66Hz 模式由设备确认，不自动开启快速模式。即使共同硬件时间映射有效，其与主机 QPC 的偏移仍不能擅自假定为零。
- 电生理默认 204800 字节，文件回放按真实长度。尚未给定真实通道、位宽、采样布局，因此 GUI 展示字节预览，不宣称真实波形解码验收通过。

## 三档与测量口径

- 三档为 `100m`、`1g`、`2g5`（也接受 `2.5g`）。首次 GUI 默认 1GbE，随后保存选择；CLI 默认 1GbE，不读取 GUI 上次选择。
- `--link-mbps 100|1000|2500` 为兼容别名，与 `--network-profile` 冲突时拒绝。V1 仍保留其原容量选项。
- 有效预算取所选档位、本机已知连接速率、已知路径上限的较小值。目标路由及绑定网卡观察在非发送关键路径中完成；环回、虚拟网卡、无线和未知路径明确标记。选择档位不修改 Windows 网卡协商设置。
- 预算按每个 UDP 应用包实际长度加 66 字节计算；DATA 一帧为 `F + 102*ceil(F/1436)`。采用累计分数预算，有界追赶，禁止积累整帧突发。
- 双路文件回放按两路实际长度联合预检；运行中实际帧长变化再次核对。预检通过仅表示容量模型未排除该配置。
- NDI 首发 15ms、电生理 18ms 保持不变；原有严格小于 1ms 的采样／包间隔偏差作为附加工程目标保留。原始计划、调整后的调度时刻、实际发送及超期分别记录，不能通过移动计划消除超限。
- 模拟／回放报告的首发时间是主机采样／播放至最后本地 send 返回。实际网卡出线和真实硬件源至发送时限分列“未检测”。
- “状态立即”没有人为增加数值阈值；记录确认至提交的实测延迟。状态业务体为不透明完整快照：GUI 可发送完整文本，CLI 周期模拟快照为四个小端 uint32（模拟格式版本、NDI启用、电生理启用、所选Mbps）。这不是实际设备状态业务格式。

## 运行示例

先启动独立参考接收：

```powershell
python tools/v2_receiver.py --bind 127.0.0.1 --port 5650 --run-id demo-v2 --report receiver-v2.json
```

再启动 Qt CLI（需 Qt 运行库环境，或从打包目录运行）：

```powershell
.\build\windows-v2-release\SimTransferCli.exe --protocol v2 --network-profile 1g --ndi-tools 40 --ep-bytes 204800 --duration 60 --run-id demo-v2 --report sender-v2.json
```

接收端退出写完报告后生成六列联合验收：

```powershell
python tools/v2_acceptance.py --sender sender-v2.json --receiver receiver-v2.json --output joint-v2.json
```

GUI 可先启动“接收与消费”，再启动同窗口发送。网络档位仅在完全停止后可修改。每轮报告独立保存在应用本地数据目录的 `v2-runs/`，可通过界面“打开每轮运行档案”查看；同名添加后缀，不覆盖旧轮次。

GUI 的联合通过要求接收基线、端点、接收会话与运行范围匹配。CLI 联合报告要求同轮标识、端点及完整计数匹配。有界数量／ID／CRC32／时间戳摘要是交付对账证据，不是逐帧逐字节相同的数学证明。协议收齐、业务消费、Qt 控件更新及物理屏幕呈现分别判断。

最终逐项测试与长测结果以配套验证报告及其原始 JSON 为准；本说明不提前宣称严格实时验收全部通过。
